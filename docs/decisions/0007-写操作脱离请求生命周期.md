## 背景

A2 的写端点（提交、Amend、回滚、加入 VCS、推送、拉取）最初把 HTTP 请求的 `AbortSignal` 传给每条 git 命令。DSH 在页面刷新、关闭标签页或连接中断时会中止该信号。评审实测：带慢 pre-commit hook 的提交在中途取消后，`git commit` 被杀，紧接着撤销 `add -N` 的 `reset` 也立即以「已取消」失败，索引里残留 intent-to-add——违反「失败后索引回到提交前」。写队列按 `requestId` 去重，还会把这个「已取消」结果回放给重试请求。

## 决定

- 写请求一旦进入写队列，就在 RPC 运行时的生命周期信号下执行到完成或超时为止，不再随 HTTP 请求取消；每条命令仍受写/网络模式的超时（60s / 180s）约束。
- 运行时卸载（插件停用、Host 退出）时中止该信号。
- 读端点仍随请求取消（结果没人要就不必算完）。

## 考虑过的其他方案

- **只让清理步骤用独立信号**：能修住 intent-to-add 残留，但提交本身仍可能在半途被杀（例如 hook 已改动文件、或 commit 对象已写入而 ref 未更新），并且去重会回放「已取消」。不选。
- **客户端在卸载前发「取消」请求**：做不到可靠（关闭标签页时请求可能发不出去），也让语义更复杂。不选。

## 影响

- 用户关掉页面后，已排队的提交/推送仍会完成；重新打开时状态栏、日志与控制台反映结果。
- 一个卡住的推送最多占用写队列 180s；需要更早中止的场景（例如用户主动「取消推送」）留待以后单独设计。
- 测试：`test/host/write-infra.test.ts`「a write keeps running after the HTTP request is cancelled」。
