# SOP：AI 主导的开发工作流

本文件规定工作怎么流转：分成哪些阶段、人在哪里把关、AI 什么时候必须停下来问、会话之间怎么交接。
目标是让大部分工作由 AI 完成，人只在少数关键节点介入。

## 1. 角色

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| 负责人 | 人 | 定目标、批准设计和计划、验收里程碑、处理升级问题 |
| 执行者 | AI（Claude Code 或 Codex） | 写计划、实现、测试、自验证、维护文档 |
| 评审者 | AI（新的会话或 subagent，不能是写这段代码的那个上下文） | 代码评审、对照计划检查 |

## 2. 工作单元

| 单元 | 粒度 | 文档 |
|---|---|---|
| 里程碑 | 可以独立运行和验收的一组能力 | 架构设计中的里程碑列表 |
| 计划 | 一个里程碑（或一次较大的改动）对应一份计划 | `docs/plans/active/<id>-<slug>.md` |
| 任务 | 计划中的一步，1–3 小时能完成，结束时 `make check` 为绿 | 计划中的任务条目 |

同一时间 `plans/active/` 中一般只有一份计划。

## 3. 里程碑生命周期

```
设计 ──[人批准]──▶ 计划 ──[人批准]──▶ 执行 ⇄ 自验证 ──▶ 评审 ──[人验收]──▶ 收尾与整理
```

| # | 阶段 | 执行者 | 产出 | 关口 | 可用技能 |
|---|---|---|---|---|---|
| 1 | 设计 | 人和 AI | 需要新设计时写 `docs/design/<日期>-<主题>.md`；已有设计足够时跳过 | **人批准** | brainstorming |
| 2 | 计划 | AI | `docs/plans/active/<id>-<slug>.md`（按 `TEMPLATE.md`） | **人批准** | writing-plans |
| 3 | 执行 | AI | 按任务循环（§4）得到代码和 commit；执行方式（subagent 驱动 / 当前会话内联）由负责人批准计划时选定 | `make check` 为绿 | subagent-driven-development / executing-plans、test-driven-development |
| 4 | 自验证 | AI | 计划「验证记录」：实际运行的命令、截图、冒烟测试结果 | 所有验收标准都有证据 | verification-before-completion |
| 5 | 评审 | AI 评审者，然后人 | 评审发现逐条处理（修复，或者写明理由后不改并登记技术债） | **人验收**：AI 演示，人确认 | requesting-code-review、receiving-code-review |
| 6 | 收尾 | AI | 见 §7 收尾清单 | `make check` 为绿 | finishing-a-development-branch |

**"人批准"的含义**：人明确回复同意。沉默、"先这样吧"、只批准了想法都不算批准当前产出。批准只对当时呈现的那一份产出有效。

## 4. 任务循环（执行阶段）

1. 在计划里把任务状态改为 `进行中`。
2. **先写测试**，运行并确认它按预期失败。
3. 实现，直到测试通过。
4. 运行 `make check`，全部通过。
5. 更新计划：勾选任务；在「进度」中追加一行；决定、意外或发现写进对应章节；更新「下一步」。
6. commit。代码和计划更新放在同一个 commit 里。

一个任务做不完时，先把「下一步」写清楚再结束会话。**计划文件永远要能让一个全新的会话接着干。**

## 5. 会话交接

- **开始**：按 AGENTS.md 的「每次会话开始时」执行。
- **结束或上下文快满时**：更新计划的「进度」和「下一步」；把未提交的工作 commit（或在「下一步」中说明为什么没提交）；不要把关键信息只留在对话里。
- **「下一步」的写法**：写成新会话可以直接执行的指令。例如"实现 `store/snapshot.py` 的 `rollback()`，测试见 `tests/store/test_snapshot.py::test_rollback_*`（已写，目前失败）"，而不是"继续做快照"。

## 6. 升级条件

遇到下列情况之一，AI **停止当前工作**，在计划的「阻塞」一节写清问题、已尝试的办法和可选方案（附推荐），然后问负责人：

1. 设计自相矛盾，或者实现时发现设计行不通。
2. 需要计划之外的新依赖，或者需要改动计划之外的公共接口。
3. 设计中的某个风险验证项，结论和预期不符。
4. 同一个问题连续尝试三种不同的修法仍未解决。
5. 任何破坏性操作：删除数据、强制改写 git 历史，或者要改动本仓库以外的文件。
6. 范围变化：发现必须做计划之外的事，才能完成验收标准。
7. 需要真实的 API key 或付费调用，而计划里没有预先说明。

不属于上面这些情况的问题，AI 自行判断处理，把理由写进计划的「决策记录」。

## 7. 收尾清单（每个里程碑结束时）

- [ ] 计划中所有任务都已勾选，「验证记录」完整
- [ ] 负责人已验收
- [ ] 计划从 `plans/active/` 移到 `plans/completed/`，状态改为 `已完成`；TODO 中对应条目移到「已完成」
- [ ] 影响范围超出本计划的决定，已写成 ADR
- [ ] [ARCHITECTURE.md](ARCHITECTURE.md) 与代码实际结构一致
- [ ] [QUALITY.md](quality/QUALITY.md) 已更新相关模块的评级
- [ ] 新发现的技术债已登记到 [tech-debt.md](quality/tech-debt.md)
- [ ] 新验证过的 SDK 行为已写进 `references/`
- [ ] AGENTS.md 中的命令和链接仍然有效
- [ ] **整理**：清理过期文档；检查是否有应该改成机器检查的文字约定；从技术债中挑一两项顺手处理，或者排进下一个计划
- [ ] 分支合并到 main（见 §8），`make check` 为绿

## 8. 分支与合并

- 每份计划一个分支，命名为 `<id>-<slug>`，推荐在独立的 git worktree 中开发。
- 每个任务至少一个 commit。pre-commit hook 运行 `make check-fast`。
- 负责人验收后，在分支上 rebase 到最新的 main，运行完整的 `make check`，然后以 `--no-ff` 合并到 main。合并前的 `make check` 必须在**合并后的代码**上为绿。
- 不 force push，不改写 main 的历史。

## 9. 快速通道（小改动）

同时满足以下条件的改动，可以不写完整计划：只涉及 3 个以内的文件；不改变公共接口；不需要新依赖；不涉及设计决定。

流程：负责人在对话里同意 → 直接在 main 上做（仍然先写测试）→ `make check` 为绿 → commit 说明中写清原因。
如果改动过程中发现不满足上面的条件，就停下来，改走完整流程。

## 10. 文档更新触发表

| 发生了什么 | 更新哪里 |
|---|---|
| 新增或移动模块，改变了依赖方向 | ARCHITECTURE.md，以及对应的依赖契约规则 |
| 做了一个影响范围超出当前计划的选择 | 新的 ADR |
| 查证或实测了外部 SDK 的某个行为 | `references/<库>.md`，注明日期和来源 |
| 发现暂时不处理的问题 | tech-debt.md |
| 新增或修改命令 | Makefile、AGENTS.md「常用命令」、runbooks |
| 新的领域术语 | glossary.md |
| 一条文字约定被反复违反 | 把它改成机器检查（lint 规则或结构测试），并在这里删去相应的文字 |
