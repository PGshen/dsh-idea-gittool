# 0010：用户传入的修订号先解析为提交 sha

## 背景

B2 的读端点（`blame`、`fileHistory`、`compare`、`diff` 的 `range`）第一次接收客户端传来的任意修订号：分支名、标签、短 sha、`HEAD~1`。修订号会进入 git 的 argv。以 `-` 开头的值可能被 git 当成选项（例如 `--output=…`）；分支在一次请求的几次 git 调用之间移动，会让同一个请求前后读到不同的提交。路径已经有固定规则（拒绝绝对路径与 `..`，放在 `--` 之后，`GIT_LITERAL_PATHSPECS=1`），修订号此前没有。

## 决定

接收修订号的端点，在做任何其他 git 调用之前，用 `resolveRevision`（`src/host/git/revision.ts`）把它解析成完整的提交 sha：

- 非字符串、空串、超过 1024 字符、以 `-` 开头、含 NUL 或换行：直接返回 `git/invalid-payload`，不调用 git；
- 其余用 `rev-parse -q --verify --end-of-options <rev>^{commit}`；不指向提交时返回 `git/invalid-payload`；
- 之后的 git 调用只使用解析得到的 sha；需要显示原文的场合（如比较页的标签）由响应另外带回原文（`CompareRev.input`）。

之后新增接收修订号的端点（B3 起），必须经过 `resolveRevision`，并补一条「以 `-` 开头的修订号返回 `git/invalid-payload`」的测试。

## 考虑过的其他方案

- **只在 argv 里加 `--end-of-options`，直接把原文交给各命令**：不选。不是所有子命令都在同一位置接受它，而且不能解决请求内 ref 移动的问题。
- **白名单正则（只允许 ref 名字符）**：不选。`HEAD~1`、`main^2`、`@{u}` 等合法写法很难用正则穷举，最终仍要 `rev-parse` 判定是否存在。

## 影响

- 好处：统一了参数注入防护；一次请求内所有 git 调用读同一个提交；错误一律是 `git/invalid-payload`，客户端处理简单。
- 代价：每个请求多一次 `rev-parse`（毫秒级）。
- 注意：分页游标里钉住的是解析后的 sha（`v1:<sha>:<offset>`）。文件历史翻页时游标里的 sha 同样经 `resolveRevision` 校验；比较翻页时要求游标里的 sha 等于本次解析出的左侧 sha，否则拒绝。
