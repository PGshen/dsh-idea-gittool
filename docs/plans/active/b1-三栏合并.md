## 目标

冲突停下来后，用户能在 Git tab 里打开全屏三栏合并窗口：左右两栏按具体分支名显示双方版本，中间 Result 可编辑；逐块接受/忽略/追加、一键应用非冲突更改、解决简单冲突，保存半成品下次接着做，应用后文件标记为已解决。冲突列表显示每个文件的 `已解决块/总块`，支持「全部简单冲突」「逐个解决 / 审查更改」（Resolve Manually / Review Changes）「还原冲突解决」。二进制和删除类冲突在窗口里降级为二选一。

## 范围

**包含：**

- **依赖**：`@codemirror/state`、`@codemirror/view`、`@codemirror/commands`（负责人 2026-10-26 已同意引入 CodeMirror 6；不带语言包、不做语法高亮），由 esbuild 内联进 `lib/client.js`。
- **Host**：读三方内容（`:1:/:2:/:3:` blob、工作区文件哈希、二进制/大小判定）；草稿读写清理（受限 git，按 ADR 0008 的方式存为 `refs/worktree/dsh-git/merge-draft/*` → JSON blob）；把 Result 写回并标记已解决（经索引，不用 `node:fs`）；还原冲突解决（`checkout -m`）；操作结束时清理草稿。
- **Client 合并模型**（纯函数）：行级 Myers diff、diff3 分块、块状态机、逐块动作、整文件动作、简单冲突判定、编辑映射、计数。
- **合并窗口**：三个 CodeMirror 视图、块色带与行内按钮、同步滚动、顶部/底部工具栏、键盘、自动进入/退出宿主全屏、文件上一个/下一个。
- **冲突列表增强**：`已解决块/总块`、「全部简单冲突」（成功/失败数）、底部「逐个解决 / 审查更改」按钮与已审查状态、行点击打开窗口、已解决行右键「还原冲突解决」。
- **Feature flag**：`mergeWindow`，关闭时冲突列表保持 A3 行为；验收通过后默认开启。
- 全部新增文案中英双语（新分区 `locales/merge.ts`）。

**不包含：**

- 块之间的连接曲线（设计 §10.3 写明 P2 可简化）：用对齐的色块代替。
- 词级高亮、语法高亮、并排 diff（B3）。
- 自动打开冲突列表/自动应用非冲突更改的设置开关（B4 设置页）。
- `conflict-marker-size` 非默认值、`merge.conflictStyle=zdiff3` 的特殊处理（窗口不读工作区里的标记，只读索引三方，见决策记录）。
- 子模块冲突（显示「在终端解决」兜底）。

## 待负责人确认

1. **草稿存储的落地方式**（已按推荐）。你选的是「Host 存到 `.git` 内」。[ADR 0008](../../decisions/0008-待恢复贮藏标记用受限-ref.md) 规定之后所有写入 `.git` 的状态都必须经受限 git、不能用 `node:fs` 直接写 `<gitDir>/dsh-git/*.json`（沙箱里的 Agent 可以预置符号链接）。所以计划按同样方式落地：草稿 JSON 用 `hash-object -w --stdin` 写成 blob，`refs/worktree/dsh-git/merge-draft/<sha1(path)>` 指向它。效果和你选的一致（刷新、重启后都能恢复，按工作树隔离），只是不是一个普通文件。**推荐按此执行**，不另写 ADR，在决策记录里引用 ADR 0008。
2. **「Review Changes」的含义**（2026-10-26 负责人按参考项目 `conflictsDialog.tsx`/`conflicts.ts` 的行为给出）：它不是单独功能，而是冲突列表底部「逐个解决」（Resolve Manually）按钮在特定情况下换的名字，二者同一个处理函数：
   - 选中的文件里还有未解决冲突 → 显示「逐个解决」；选中的都已解决、但还有文件**未审查** → 显示「审查更改」；全部已解决且都审查过 → 按钮隐藏，「接受并完成」成为主按钮，提示「所有冲突都已解决」。
   - 点击后依次为每个文件打开三栏合并窗口：先选中的文件，再未解决的文件，最后已解决但未审查的文件；在某个窗口里取消（返回不应用），后面的文件不再打开。
   - 「全部简单冲突」自动解决的文件标为「已解决但未审查」；在合并窗口里打开过的文件、或整文件采用一侧（含列表行内「采用 …」）的文件标为「已审查」。审查可跳过：冲突都解决后「接受并完成」直接可用。
3. **Result 栏的初始内容**。按 IntelliJ 与设计底栏「应用非冲突更改」按钮的含义：Result 从 **base** 开始，所有改动（含非冲突的）都以待处理块呈现，由用户逐块接受或一键「应用非冲突更改」。备选是从 git 自动合并后的内容开始（非冲突改动已应用，只剩冲突块）。**推荐从 base 开始**（与 IntelliJ 一致，Agent 改动可逐块审）。——已按推荐。
4. **执行方式**（已按推荐）：subagent 驱动，T1 先做（冻结契约与 spike 结论），之后 T2/T3（Host）与 T4（Client 模型）可并行，T5→T6→T7 串行。

## 契约（T1 冻结）

新增端点（读 1、写 3），类型写在 `src/shared/protocol.ts`，T1 登记并先返回 `not implemented`：

| 端点 | 类型 | 请求 | 响应要点 |
|---|---|---|---|
| `mergeFile` | 读 | `{ path }` | `MergeFileValue`：`path`、`kind: ConflictKind`、`base/ours/theirs: MergeSide \| null`（`MergeSide = { blob: string; text: string \| null; binary: boolean; size: number }`，`text` 为 null 表示二进制或超限）、`tooLarge: boolean`、`worktreeSha: string \| null`（工作区文件 `hash-object`，文件不存在为 null）、`draft: MergeDraft \| null`、`draftStale: boolean`、`resolved: boolean`（已解决路径，三方来自 resolve-undo）、`version` |
| `mergeDraftSave` | 写 | `{ path, draft: MergeDraft }` | `{ path, version }`；`draft.stages` 与当前索引不符 → `git/stale-target`（target `conflict`） |
| `mergeApply` | 写 | `{ path, result: string, stages: MergeStageShas, expectedWorktreeSha: string \| null }` | `ResolveConflictValue`（`path`、`remaining`）；三方或工作区哈希不符 → `git/stale-target`；成功后删除该路径草稿 |
| `unresolveConflict` | 写 | `{ path }` | `{ path, remaining, version }`；`git checkout -m -- <path>`，路径不在已解决列表 → `git/stale-target`；没有 resolve-undo 信息 → `git/exec-failed` + 提示在终端处理 |

```ts
interface MergeStageShas { base: string | null; ours: string | null; theirs: string | null }
type MergeChunkState = 'pending' | 'left' | 'right' | 'both-left-first' | 'both-right-first' | 'ignored' | 'edited'
interface MergeDraft {
  version: 1
  stages: MergeStageShas
  result: string
  /** 与 diff3 分块一一对应（按块序号），加载时块数不一致即作废。 */
  chunks: Array<{ state: MergeChunkState; leftDone: boolean; rightDone: boolean }>
  savedAt: string
}
```

`mergeFile`/`mergeApply`/`mergeDraftSave`/`unresolveConflict` 加进 `RPC_ENDPOINTS`；后三者进 `WRITE_ENDPOINTS`。块计数不另建批量端点（决策 D4）。

### T4：Client 合并模型（完成）

- **目标**：React-free、CodeMirror-free 的纯模型，承载全部块逻辑。
- **涉及文件**：`src/client/merge/line-diff.ts`、`src/client/merge/diff3.ts`、`src/client/merge/merge-model.ts`（均新）、`test/client/merge/*.test.ts`。
- **接口与要点**：
  - `splitLines(text: string): string[]`：保留行尾（`\n`/`\r\n`），末行无换行也保留。
  - `diffLines(a: string[], b: string[]): DiffOp[]`：Myers O(ND)，`DiffOp = { aStart; aEnd; bStart; bEnd }`（只列变化区间）。
  - `diff3(base, ours, theirs): MergeChunk[]`：`MergeChunk = { id: number; kind: 'left-only' | 'right-only' | 'same-change' | 'conflict'; base: Range; left: Range; right: Range }`（行区间，半开）；相邻/重叠的变化区间合并为一个 conflict 块。`same-change` 视为非冲突。
  - `isSimpleConflict(chunk, base, ours, theirs): boolean`：对块内文本做字符级 diff3，没有重叠修改即为简单；同时返回合并后的文本 `simpleMerge(...)`。
  - `MergeModel`（不可变值 + 纯函数）：`createModel(sides, draft?)`；Result 文本初始为 base（决策待确认 3）；每块在 Result 中的当前区间 `resultRange`；动作 `acceptLeft/acceptRight/ignore(side)/appendBoth(order)/resolveWhole(side)`（Ctrl+点击）、`applyNonConflicting('left'|'right'|'all')`、`resolveSimple()` → `{ model, resolved: number }`、`acceptFile(side)`、`revert()`；`applyEdit(model, from, to, insert)`：映射全部块区间，落在块内（或跨块）的编辑把这些块标 `edited`；`counts(model) → { resolved; total }`（只计 conflict 块）；`nextUnresolved(model, fromChunk, dir)`；`toDraft(model, stages)` / 从草稿恢复（块数不一致返回 null）。
  - 块动作后的 Result 拼接规则：块 `pending` 时 Result 中是 base 文本；`left` = 左侧文本；`both-left-first` = 左 + 右；`ignored` 保持当前文本。
- **测试**（先写）：diff 正确性（空、全同、全不同、末行无换行、CRLF 混合）；diff3 分块（左单改、右单改、同改、重叠冲突、相邻冲突、AA 无 base、文件末尾追加）；每个动作对 Result 与计数的影响；手动编辑映射（块前、块内、跨两块、删除整块）；`edited` 块不受批量动作影响；简单冲突判定（同一行左右改不同单词 = 简单；改同一词 = 不简单）；草稿往返。
- **验证命令**：`make check`

- 2026-10-26 — D8（T4）合并模型的细节裁定：
  - **块状态与 `leftDone`/`rightDone`**：`state` 表示块在 Result 中当前是什么文本（`pending`/`ignored` = base，`left`/`right`，`both-*-first` = 两侧按序拼接，`edited` = 用户文本）；`leftDone`/`rightDone` 表示该侧的改动是否已被处理（应用或明确忽略）。单侧块中没有改动的一侧初始即为 done。块「已解决」= `edited` 或两侧都 done；`counts` 只计 `conflict` 块。
  - **接受一侧**：另一侧文本已在位（`state` 为另一侧）时追加在其后（`both-*-first`），否则替换；`same-change` 接受任一侧即两侧都 done。`ignore` 只把该侧标 done，`pending` 变 `ignored`，文本不变。`appendBoth` 只在两侧都未处理时可用。`resolveWhole`（Ctrl/Cmd+点击）直接替换为该侧文本并两侧都 done（另一侧已应用时也是替换而非追加）。拼接时前一段末行没有换行则补一个换行（取文件的行尾风格）。
  - **`edited`**：手动编辑涉及的块变 `edited` 并清空两侧 done；`resolveSimple` 也写成 `edited`，但两侧 done 置 true——二者由 `isManuallyEdited` 区分（不扩展冻结的 `MergeChunkState`）。`edited` 块不接受任何块动作与批量动作（T6 隐藏其按钮），只有整文件 `acceptFile`/`revert` 和撤销会改动它。
  - **编辑映射**（行级）：编辑替换旧行 `[es, ee)`；与非空块重叠即涉及该块；纯插入整行（`es === ee`）只在严格落在块内部时涉及，所以在块首行行首回车只是平移块；空块（纯插入块待处理时）只在编辑替换的行严格包含其位置时涉及，在其位置纯插入整行（含回车）只平移它（控制者裁定 10，修复「回车静默解决插入块」）。被涉及的块扩展到覆盖编辑后的行；一次编辑跨多块时由第一块占有共享行，区间保持有序不重叠。
  - **简单冲突**：brief 写「字符级」，实际按词切分（`[\p{L}\p{N}_]+`、`\r\n`、其余单字符）做 diff3：同一行改不同单词为简单，同一个词内改不同字母不简单（按字符会被误判为可合并），与 IntelliJ 的按词比较一致。重叠或相邻的修改都算冲突；块的 token 总数超过 60 000 不判简单。
  - **草稿恢复**（已被 D9 修订）：没有行区间的旧草稿恢复时用「base 间隙 + 各块按状态推出的文本」作模板，与草稿 Result 做行 diff 映射出区间；块外未被手改时与保存前完全一致（`edited` 块以 base、自动解决块以 `simpleMerge` 结果作对齐提示）。版本不符、块数不符、状态值未知、状态与两侧标记或块类型矛盾（如 `both-left-first` 但 `leftDone` 为 false、右单改块为 `left`、单侧块中未改动的一侧未 done）→ 返回 null（控制者裁定 10）。`toDraft` 的 `savedAt` 可注入（测试确定性）。
  - **性能保护**：Myers 单次 bisect 的编辑代价上限 4096，超出时把该区域整体当作一次替换（两个无关的 20 000 行文件也能在百毫秒级完成，代价是块更粗）。
  - **`nextUnresolved`** 遍历所有未解决块（不只是冲突块，非冲突改动也需要处理），`fromChunk = null` 从头/尾开始，不回绕（到末尾由 T6 提示下一个文件）。
- 2026-10-26 — D9（T4 评审，控制者裁定 9）草稿记录每块在 Result 中的行区间：`MergeDraft.chunks` 的元素类型命名为 `MergeDraftChunk`，新增可选 `resultStart`/`resultEnd`（半开行区间，两者同时出现或同时缺省；共用校验 `validDraftChunkRange`：非负整数且 start ≤ end）。原因：只靠文本对齐恢复区间在重复行处会放错非编辑块（评审探针：base `A\nA\nz\n`、ours 把第二行改成 `B`，删掉第一行后恢复，区间从 [0,1) 变成 [1,1)，再「接受左侧」得到错误文本）。`toDraft` 总是写区间；恢复时有区间就直接用并校验（有序、不重叠、在 Result 内、每个非 `edited` 块的行等于其状态文本），任一不符返回 null（按草稿作废处理）；只有完全没有区间的旧草稿才走文本对齐；部分块有区间也返回 null。Host 的 `mergeFile` 草稿校验与 `mergeDraftSave` 载荷解析接受这两个可选字段（格式不符分别按作废 / `git/invalid-payload` 处理），这是对冻结契约的向后兼容扩展。

- 2026-10-27 — D12（T7）冲突列表增强与 Review Changes 的实现裁定：
  - **已解决文件的 Result**：契约的 `mergeFile` 只给工作区哈希、不给工作区文本，所以客户端按哈希解释工作区：草稿的 Result 哈希等于 `worktreeSha` 时用草稿；否则依次试「自动合并重放（`autoMerge`）」「整文件采用左 / 右」，哈希一致的那个保留其块状态；都不一致时用 HEAD（= stage 2，ours）+ `diff staged` + `diff worktree` 重建工作区文本，哈希校验通过后作为 Result，全部块标 `edited`（`editedModel`：第一块覆盖整个 Result，其余为末尾空区间）；仍不行（diff 截断 / 二进制）就按读取失败处理（`merge.error.worktreeUnreadable`），在 Review 队列中静默跳过。哈希是 `git hash-object` 的 blob id，用纯 JS SHA-1（`crypto.subtle` 是异步的，且非安全上下文不可用）。已解决文件的旧草稿只有 Result 等于工作区时才用，否则忽略（不报作废）。
  - **已审查语义**（D5 的落地）：`conflict-store` 记录本轮「见过的未解决文本冲突」（`seen`）；它们变为已解决后，不在 `reviewed` 里的就是「未审查」——包括「全部简单冲突」写回的、行内「标记已解决」的、在终端或被 Agent `git add` 的。没见过就已解决的文件（页面刷新前解决的，或从未冲突、自动合并的路径）一律按已审查处理，这同时满足 D5 的刷新兜底和裁定 6/7（从未冲突的路径没有 resolve-undo、不可审查）。轮次键 = `operationIdentity` + 变基步号（每一步的冲突与 resolve-undo 不同），换轮次清空。加入已审查：窗口加载成功（`onOpened`，整文件采用一侧总在打开的窗口里发生，已被覆盖）、行内「采用 …」成功；「全部简单冲突」写回的文件从已审查中移除。删除类与 `added-by-*` 冲突不进 `seen`（resolve-undo 不全，打不开）。
  - **底部按钮**：`manualButton`：选中里有未解决 → 逐个解决；没有选中且还有未解决 → 逐个解决；否则有未审查的已解决文件 → 审查更改；否则还有未解决 → 逐个解决；否则隐藏（「接受并完成」为主按钮并显示「所有冲突都已解决」）。`reviewQueue`：选中的（按列表顺序；已审查的也算，用户点名）→ 其余未解决 → 已解决未审查，去重保序；已知不可审查的已解决文件不进入。队列由 `createReviewRunner` 推进：应用成功或降级视图二选一完成 → 下一个；队列走完 → 冲突列表；返回、手动切换文件、其他入口替换窗口 → 停止。已解决文件打开失败（`git/stale-target` 或工作区读不出）→ 标记不可审查并跳到下一个。
  - **「全部简单冲突」**：只处理 `both-modified` / `both-added`；有草稿的文件视为有人在处理，跳过（计入「需要手动处理」）；删除类、二进制、超限、写回失败都计入 M。
  - **「还原冲突解决」**：对所有已解决行提供（右键、`Shift+F10` / ContextMenu 键），菜单沿用 ADR 0006 材质与 `useFloatingMenu`；`git/exec-failed`（删除类）提示「请在终端处理」，`git/stale-target`（没有冲突记录，如从未冲突的路径）提示「没有可还原的冲突记录」并刷新列表。没有用 `mergeFile` 预探测来隐藏菜单项（每行一次 RPC，代价不值）。
  - **块计数缓存**：计数按路径存在 `ConflictReview.counts`，窗口离开、应用、还原、全部简单冲突后作废该路径；重新加载时 stages 与草稿都没变就复用上次的计数（不重算 diff3）；轮次变化全部清空。
  - **未保存的窗口被其他入口替换**（T6 评审遗留）：覆盖层控制器新增 `guard`（`open` / `close` 前询问，`closeIf` 不问——它跟随已经结束的操作），工作台在当前是合并窗口时问窗口的 `guardLeave`：有未保存改动就显示离开询问，保存或丢弃后再执行原来的导航。窗口自己的离开（返回、切文件、外部）先 `store.discard()`，所以后续导航不会被再问一次。

## 意外与发现

- `sidebarRight` 服务没有公开读取当前是否全屏的方法（`service.ts:618-625` 只有 `toggleFullscreen`），T1 验证用面板宽度判断；若不可靠，备选是只在「窗口自己进入」时记账，用户手动全屏的情况下打开窗口不再 toggle（需要实测）。
  - **T1 更新**：tab 正文有公开读取——框架注入的 `useTabInfo()` 返回 `sidebar.fullscreen`（含 <768px 自动全屏，`tab-info.ts:42`、README:84），`GitBody` 已在用该 hook；面板根元素还有 `data-sidebar-right-panel="fullscreen"`。宽度启发式在 Windows 标题栏模式下会误判，降为最后备选。T6 实测后定稿（[可行性调研 §14](../../references/dsh-integration-feasibility.md)）。
- **删除类冲突不能用 `checkout -m` 还原**（T1 实测）：DU 用 `git rm`、UD 用 `checkout --ours` + `add` 解决后，`checkout -m` 报 `does not have all necessary versions`（退出 1，什么都不改）。文本冲突（合并/变基/拣选，含经 `update-index --cacheinfo` 写回的）都能还原，AC9 成立。删除类冲突可用 `update-index --unresolve -- <p>` 恢复索引 + `checkout --ours|--theirs -- <p>` 写回工作区（已实测）。T1 不改契约；按契约现状这类路径得到 `git/exec-failed` + 在终端处理，是否扩展待决定（见「下一步」）。
- **resolve-undo 不随操作结束清除**：合并提交后仍在，切分支、开始下一次合并、变基进入下一步时才清空。所以只有「操作进行中且路径在本次已解决列表」时才能用它（契约的 `git/stale-target` 校验正好挡住）。另外 `operationState.resolved` 含自动合并、从未冲突的路径，这些路径没有 resolve-undo（T2/T7 注意）。
- `checkout -m` 重新写出的标记标签是字面的 `ours`/`theirs`，不是分支名；窗口只读索引三方（D2），不受影响。
- 包体积：CodeMirror 按计划用到的 API 不压缩约 595 KB（gzip 148 KB），会让 `lib/client.js`（当前 727 KB）接近翻倍；压缩后约 278 KB（gzip 91 KB）。T6 引入后复测，若负责人在意体积可另议是否给 client 产物开 minify（不在本计划范围）。
- 全新 checkout/worktree 里 `pnpm build` 失败：`ENOENT: open 'lib/client.js'`——客户端构建 `write: false`，esbuild 不建目录，`build.mjs` 直接写文件。T1 在写文件前补 `mkdirSync('lib', { recursive: true })`。
- 单测没有 DOM 环境（无 jsdom/happy-dom），T1 不写 CodeMirror 挂载测试；T5/T6 需要时另议（引入 DOM 环境是计划外依赖）。
- worktree 里运行 `pnpm install/add` 会把 `pnpm-lock.yaml` 的 DSH `link:` 路径改写成相对 worktree 的 `../../../../deepseek-harness/...`；提交前改回 `../deepseek-harness/...`，否则主 checkout 的锁文件会失效。
- **T2 判定细节**：已解决路径须「操作进行中（非 bisect）且 resolve-undo 同时含 stage 2 和 3」（见 D7，已解决的 DU/UD 不可打开）；二进制判定用「含 NUL 或解码出 U+FFFD」，没有再调 `diff --numstat`（gitattributes 标为 binary 的文本仍按文本处理，写回走索引不受影响）；超过 2 MiB 的一侧先 `cat-file -s` 判断、不读内容，所以 `binary` 恒为 false（无法得知）；`mergeFile` 不走版本缓存，每次现读（工作区可能被 Agent 改动）。
- **T3 判定细节**：(1) 工作区哈希变化的 `git/stale-target` 沿用 `target: 'conflict'`（协议的 target 联合没有 worktree，不改冻结契约），用 `details.reason` 区分：`worktree-changed` / `stages-changed`。(2) `unresolveConflict`（裁定 4）：路径仍在 `ls-files -u` 或操作未进行/无 resolve-undo 记录 → `stale-target`；resolve-undo 缺 stage 2 或 3（删除类）→ `exec-failed` + `details.reason: 'delete-kind'`，不做 `update-index --unresolve` 回退。(3) `mergeApply` 的文件模式取 stage 2（缺则 3）的 mode，非 100644/100755（符号链接、子模块）→ `exec-failed`。(4) 草稿清理尽力而为（吞掉错误）：操作结束删全部，操作仍在进行时按「不在 `ls-files -u`」删，所以变基下一步仍冲突在同一路径时旧草稿也会被删（stages 本就不会匹配）；`mergeApply` 删自己那条草稿。(5) `deleteRefs` 用 `for-each-ref` 列出再一次 `update-ref --stdin` 事务删除，支持前缀数组与 keep 集合。

- **T6**：单测仍然没有 DOM 环境（不引入 jsdom/happy-dom，计划外依赖）。组件测试用 `renderToStaticMarkup` 测视图；编辑器与 store 的往返用 `@codemirror/state` 的 `EditorState`（不需要 DOM）测；`createMergePane` 等 DOM 部分留给 T8 实机。

- **T6**：`lib/client.js` 726,900 → 1,412,443 字节（+685,543；gzip 143,059 → 311,093），即 CodeMirror（约 595 KB）+ 合并模型/store/窗口。是否给 client 产物开 minify 仍待负责人决定（T1 已记）。
