## 背景

`/dsh-git` 路由（ADR 0004）对所有端点统一限制请求体为 256 KiB，以免浏览器端或页面脚本把大请求体塞进 Host 进程。B1 的合并窗口允许打开每侧最多 2 MiB / 20 000 行的文件，`mergeApply`/`mergeDraftSave` 的 Result 上限是 8 MiB（JSON 转义后最坏约 16 MiB，草稿还带最多 100 000 个块描述）。负责人验收演示中，1.7 MB 的文件能打开却既不能应用也不能保存草稿，界面只显示「HTTP 400」。端到端测试直接调用处理器、绕过了 HTTP 层，所以没测出来。

## 决定

请求体上限按端点决定：`mergeApply`、`mergeDraftSave` 为 32 MiB（`4 × MERGE_APPLY_RESULT_MAX_BYTES`，覆盖最坏转义加草稿开销并留余量）；其余端点保持 256 KiB。读取时逐块累计字节，超限立即中止读取，返回 HTTP 413 与 `git/invalid-payload`（`details.reason: 'body-too-large'`）；客户端优先展示非 2xx 响应里的结构化错误，`body-too-large` 映射为「内容太大……请在终端处理」。之后新增需要大请求体的端点，必须在这里显式登记上限，并补一条经真实 HTTP 的测试。

## 考虑过的其他方案

- **统一调大全局上限**：不选的原因：其它端点只传路径和小表单，没有理由放开；按端点登记让大请求体成为显式决定。
- **把 Result 上限降到 256 KiB 以内**：不选的原因：合并窗口能打开的文件远大于此，用户会遇到「能看不能改」；是否把 Result 上限降到 2 MiB 仍在 TODO 中待定，与本决定兼容。
- **分片上传**：不选的原因：本地插件端点，单次 32 MiB 以内足够，分片的复杂度不值得。

## 影响

- 好处：窗口能打开的文件都能保存与应用；超限时用户看到可理解的提示。
- 代价：单个合并写请求最坏会在 Host 里占用约 32 MiB 缓冲加解析副本（约 100 MB 瞬时）；端点只监听本机并经 DSH 鉴权，可接受。
- `test/host/http.test.ts` 用真实 `node:http` 服务器覆盖 2 MiB 请求被接受、超限 413、普通端点仍为 256 KiB。
