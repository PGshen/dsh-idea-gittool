## 背景

合并、变基、拣选、回滚、拉取、更新项目、签出在工作区有未提交的已跟踪改动时，用户可以选择「贮藏并继续」。如果操作停在冲突，Host 必须记住这条贮藏属于哪次操作，等操作完成或中止后自动恢复；这个记忆要在多次 continue 和 Host 重启后仍然有效，且「贮藏永不丢」。

约束：Host 的所有写入都经 `sandbox.confine` 限定在工作区写边界内；沙箱里的 Agent 可以在 `.git` 里预置符号链接。

## 决定

待恢复标记是两个 ref，只通过受限 git 的 `update-ref` 读写：

- `refs/worktree/dsh-git/pending-stash`：指向贮藏提交。
- `refs/worktree/dsh-git/pending-stash-meta`：指向一个 JSON blob，保存 `{ operation, branch, headSha, createdAt }`。

恢复规则：只有标记里的操作类型与当前操作一致、且 HEAD 分支匹配时才恢复，并且始终按 sha 在贮藏列表里定位。`stashApply`/`stashDrop` 处理到这条贮藏时同时删除两个 ref。

## 考虑过的其他方案

- **`<gitDir>/dsh-git/pending-stash.json`（Host 用 `node:fs` 直接写）**：不选的原因：绕过 `sandbox.confine`；沙箱内 Agent 预置的符号链接会让写入覆盖仓库外的文件（T2 评审发现）。
- **共享的 `refs/dsh-git/*`**：不选的原因：多个工作树共享同一命名空间，一个工作树的操作会误恢复另一个工作树的贮藏。
- **`refs/worktree/dsh-git/*` + 受限 `update-ref`**：选用。按工作树隔离，写入经 confine，标记自带可达性。

## 影响

- 好处：所有写入都在沙箱边界内；标记随仓库走、Host 重启后有效；ref 让贮藏提交保持可达，即使用户手动 drop 了贮藏条目也能从标记找回。
- 代价：新的智能操作写标记会覆盖旧标记，旧贮藏仍在贮藏列表里但不再自动恢复；`stash push` 成功到标记写入之间 Host 崩溃，贮藏仍在列表中（信息可辨认）但不会自动恢复。
- `update-ref` 目前没有旧值检查，登记为 TD。
- 之后任何要写入 `.git` 的状态都必须经受限 git，不再使用未受限的 `node:fs`。
