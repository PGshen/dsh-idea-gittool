## 目标

用户在 Git tab 里能完整管理分支（签出/智能签出/新建/重命名/删除/合并/变基/拉取/获取/更新项目）、管理贮藏（创建/应用/弹出/删除/预览），并能把一次合并、变基、拣选、回滚走完：脏工作区时先问再贮藏、冲突时按具体分支名逐文件采用一侧、标记已解决、继续或中止、在提交页提交合并结果。顺带收掉 TD-5（嵌套 refs 监听）、TD-8（回滚只删确认过的未跟踪文件）、TD-9（大批量路径）、TD-10（force-with-lease 带期望值）。

## 范围

- **A2 遗留与技术债**：TD-5 嵌套 refs 监听；TD-8 `confirmedUntracked`；TD-9 路径改走 stdin（`--pathspec-from-file`）+ 客户端超限提示；TD-10 `expectedRemoteSha`。

### T2：Host 智能贮藏与操作控制（完成）

- **目标**：所有「可能停在冲突」的操作共用一套贮藏/恢复与继续/中止，并把操作详情交给客户端。
- **涉及文件**：`src/host/git/smart-stash.ts`（新，自 `pull.ts` 抽出）、`src/host/git/operation.ts`（新）、`src/host/git/pull.ts`、`src/host/git/status.ts`、`src/host/rpc.ts`、`src/shared/protocol.ts`、`test/host/{smart-stash,operation}.test.ts`。
- **接口与要点**：
  - `withSmartStash(ctx, { stash: boolean, operation: SmartOperationKind }, run)`：有未提交的**已跟踪**改动且 `stash !== true` → `git/dirty-worktree`（`details.paths` ≤50 条 + `count`）；`stash === true` 时 `stash push -m 'dsh-git: before <operation>'`，记下贮藏 sha，执行 `run`；成功后 `stash pop --index`（失败退回内容恢复，再失败报 `git/conflict` + `details.stashKept: true`）——行为与 A2 `pull.ts` 现有逻辑一致，`pull.ts` 改为调用它；A2 冲突详情里的 `autostash: true` 统一改名为 `stashKept: true`（客户端目前没有读取该字段，改名无兼容负担）。
  - **待恢复贮藏持久化**：`run` 停在冲突时，把 `{ stashSha, operation, createdAt }` 写到 `<gitDir>/dsh-git/pending-stash.json`；`operationControl` 在操作结束（continue 走完或 abort）后读取并按 sha 恢复（`stash list --format=%H` 找到对应 `stash@{n}`，找不到 → 不报错，返回 `stashMissing: true`），然后删除标记。Host 重启后仍有效。
  - 端点 `operationState { sessionId }`（读）→ `OperationStateValue { operation, ours: ConflictSide, theirs: ConflictSide, step?: { current, total }, message?: string, conflicts: FileEntry[], resolved: string[], pendingStash: boolean }`；`ConflictSide = { label: string, ref?: string, sha?: string }`。来源：合并 `MERGE_HEAD` + `MERGE_MSG` 中的分支名（解析不到用短哈希）；变基 `rebase-merge/{head-name,onto,msgnum,end}`（或 `rebase-apply` 对应文件）；拣选/回滚 `CHERRY_PICK_HEAD`/`REVERT_HEAD`。`resolved` = 本次操作中已无冲突、相对 HEAD 有暂存改动的路径。
  - `StatusValue.operationStep?: { current, total }`（变基进度，横幅用；从 `operationState` 同一读取函数取，开销只有两个小文件）。
  - 端点 `operationControl { sessionId, requestId, action: 'continue' | 'skip' | 'abort' }`：合并 continue = `commit --no-edit`（不带 pathspec，等同 `merge --continue`）；拣选/回滚 `--continue`/`--skip`/`--abort`；变基 `--continue`/`--skip`/`--abort`；`skip` 只对变基与拣选有效；仍有冲突时 continue → `git/conflict`（`details.conflicts` 数量）；continue 后又停在下一个冲突 → `git/conflict`（客户端刷新冲突列表）。
  - 端点 `operationCommit { sessionId, requestId, message }`：仅合并中可用（否则 `git/invalid-payload`）；`commit -F -`（信息走 stdin）且不带 pathspec；有未解决冲突 → `git/conflict`。
- **测试（真实临时仓库）**：脏工作区无 `stash` → `dirty-worktree`；贮藏 → 合并成功 → 恢复且暂存保留；合并冲突 → 标记文件存在 → abort 后贮藏恢复、标记删除；continue 完成后恢复；贮藏被用户手动删掉后 `stashMissing`；变基 2/3 进度与 head-name/onto；拣选/回滚的 ours/theirs 标签；`operationCommit` 冲突未清零被拒、清零后不带 pathspec 成功；`pull.ts` 原有测试全部仍过。
- **完成标准**：AC5、AC6、AC8 的 Host 部分有测试证据；`make check` 绿。
- **验证命令**：`pnpm vitest run test/host/smart-stash.test.ts test/host/operation.test.ts test/host/pull.test.ts`。

### T3：Host 分支写操作与冲突解决（完成）

- **目标**：签出、新建、重命名、删除，以及冲突文件的逐文件解决。
- **涉及文件**：`src/host/git/branch-write.ts`（新）、`src/host/git/conflict.ts`（新）、`src/host/rpc.ts`、`src/shared/protocol.ts`、`test/host/{branch-write,conflict}.test.ts`。
- **接口与要点**：
  - `checkout { sessionId, requestId, target: { kind: 'local' | 'remote' | 'tag' | 'revision', name: string }, mode?: 'normal' | 'stash' | 'force' }` → `{ branch: string | null, detached: boolean, head: string, stashRestored?: boolean }`。local → `switch <name>`；remote `origin/x` → 有本地 `x` 时 `switch x`，否则 `switch -c x --track origin/x`；tag/revision → `switch --detach <ref>`。`normal` 下 git 报「would be overwritten」→ `git/would-overwrite`（`details.paths`）；`stash` 走 `withSmartStash`；`force` → `switch --discard-changes`。修订号先 `rev-parse --verify --end-of-options <rev>^{commit}`。
  - `createBranch { name, startPoint, checkout }`：`check-ref-format --branch`；已存在 → `git/branch-exists`；`branch -- <name> <start>` 或 `switch -c`。
  - `renameBranch { from, to }`：`branch -m -- <from> <to>`；目标已存在 → `git/branch-exists`。
  - `deleteBranch { name, force }`：当前分支 → `git/invalid-payload`；`-d` 报未合并 → `git/not-merged`（`details.branch`）；`force` 用 `-D`。

## 评审重点（自验证与 AI 评审时特别关注）

- **贮藏永不丢**：智能操作的任何失败路径（冲突、超时、Host 重启、用户手动删贮藏、continue 后又冲突）都不能 drop 用户的贮藏；恢复失败一律保留并告知。`pending-stash.json` 与真实贮藏不一致时以 sha 为准。
- **ours/theirs 方向**：变基时 `--ours` 是目标分支。冲突列表的「采用 main」必须真的得到 main 一侧的内容——三类操作各有一条真实仓库测试按内容断言，不能只断言调用了哪个参数。
- **不打开编辑器、不挂起**：merge/revert/cherry-pick/rebase continue、`commit` 在操作状态下都不能等编辑器或终端输入（`GIT_EDITOR=true` 已在写环境，另加 `--no-edit`）；任何 git 等待 stdin 都会表现为 60s 超时。
- **目标漂移**：status 是 3s 前的快照。删除分支、删贮藏、采用冲突一侧、重置时，目标可能已经变了——Host 以执行时的事实为准（贮藏按 sha、冲突按当前列表、重置前重新读 HEAD），对不上就 `git/stale-target`，不对着意料之外的对象操作。
- **用户输入当选项**：分支名、修订号、远程名以 `-` 开头或含空白时不能被 git 当成选项；每条命令用 `--end-of-options` / `--` 分隔，Host 先校验。
