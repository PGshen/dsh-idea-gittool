# 0014：git 路径的信任边界

## 背景

B4d 按负责人的决定，让用户在设置里填 git 的绝对路径：路径存在浏览器里，Git 标签挂载时经 `gitExecutable` 端点交给 Host，Host 校验通过后在进程内存里替换要运行的 git。

整分支终审指出，这等于让任何能调用插件 RPC 的页面代码（包括同一 DSH 页面里的其他客户端插件）选择 Host 运行哪个程序。而 Host 的读命令不经沙箱：一个被采用的假 git 会在每 3 秒一次的轮询里、在沙箱之外运行。最现实的路径是 Agent（可能被提示注入）在会话工作区里写一个打印 `git version …` 的可执行文件，再引导用户把它设成 git 路径。初版校验只看「绝对路径、可执行、`--version` 像 git」，而且为了看 `--version` 先运行了它。

## 决定

保留负责人选的方案（客户端存、Host 内存采用），但把校验收紧成下面的顺序。**前 5 步都通过之前不运行任何东西**：

1. 绝对路径；Windows 上拒绝 UNC/网络路径（`\\…`、`//…`）。
2. 文件名必须是 `git` 或 `git.exe`（不区分大小写），原样和 `realpath` 之后都要满足。
3. `realpath` 之后的文件不能位于会话的沙箱工作区内（`sandboxPolicy.workspaceRoot`），工作区里的文件可能是 Agent 写的。
4. 是普通文件且可执行。
5. 记下 `realpath` 文件的身份（设备号、inode、大小、mtime）。
6. 运行 `<realpath> --version`，必须输出 `git version …` 且不低于最低版本。
7. 之后运行的是 `realpath`，而不是用户填的路径。执行器在每条命令前比对文件身份，文件被替换就不再运行，报 `git/not-found`。

## 考虑过的其他方案

- **只由 Host 环境变量指定（`DSH_GIT_PATH`）、客户端只读显示**：攻击面最小，但用户要改 DSH 的启动方式，「找不到 git」时无法在界面里自助解决。这是负责人待确认 1 的备选 A，未采用。
- **只允许系统目录**（`/usr/bin`、`/opt/homebrew`、`C:\Program Files\Git` 等白名单）：会误伤 asdf/nix/自编译安装，不同平台的列表也难以维护。
- **路径持久化到 Host 的文件**：不能解决「谁能调用端点」的问题，还要新的存储位置。

## 影响

- **仍然存在的风险**：页面上能调用插件 RPC 的代码，可以把 git 指向工作区之外一个已存在、名为 `git` 的可执行文件。这要求攻击者已经能在工作区外写文件，或者那里本来就有这样的文件；这种能力已经超出本插件能防的范围。
- **对用户的影响**：放在工作区里的 git（例如项目自带的工具链）不能用作 git 路径，提示要求选择系统安装的 git。
- 「打印 git 版本的任意程序」不再能通过校验，因为文件名和位置检查在运行之前。
