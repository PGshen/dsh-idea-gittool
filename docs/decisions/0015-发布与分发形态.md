## 背景

插件功能已按 A/B 阶段完成，需要分发给其他 DSH 用户使用。DSH 的 `dsh plugin add` 接受四类安装来源：绝对路径或本地 tarball、tarball URL、registry 包名、git 地址。本项目有两个约束：

- `lib/` 是构建产物、被 `.gitignore` 忽略，仓库里没有 `prepare` 脚本；从 git 地址安装会拿到没有产物的源码，用户还得在 `pnpm-workspace.yaml` 里放行构建脚本。
- 分发对象是公开的所有 DSH 用户，不是内部小范围；需要许可证、元数据、可校验的产物和撤回办法。

负责人选定：先走 GitHub Release 附件 tarball，`1.0.0-rc.1` 作为首个公开预览，许可证用 Apache-2.0。

## 决定

1. **首发载体是 tarball**：`make dist` 产出 `dist/dsh-idea-gittool-<版本>.tgz` 与 `SHA256SUMS`；GitHub Release 上传这两个附件。
2. **收件人用 URL 安装**：`dsh plugin --profile web add <Release 附件 URL>`，重启 `dsh web`；Web 侧边栏 **Plugins → Add plugin** 接受同一 URL 或本地 tgz 的绝对路径。
3. **不把 `dsh plugin add github:…` 写进安装文档**：仓库没有构建产物与 `prepare`，该路径对用户是半坏的。
4. **许可证 Apache-2.0**：包内含 `LICENSE` 与 `NOTICE`；README 保留对 IntelliJ 工作流与 IdeaGitTool 功能清单的致谢。参考项目 checkout 已不可用，未发现代码级复用，按「未复制」处理；若日后确认复用，再补源文件署名。
5. **npm 发布暂不做**：`prepublishOnly` 已就位（跑 smoke），元数据齐全，但发布动作与 registry 选择留到 rc 反馈之后。
6. **版本与兼容**：`1.0.0-rc.1` 是公开预览；`engines.dsh` 保持 `>=0.2.1-rc.2 <0.3.0`，DSH 升到 0.3 前必须发兼容版本。
7. **远程动作由负责人执行**：`git push`、打 tag、GitHub Release 上传；AI 只准备产物与命令。

## 考虑过的其他方案

- **只发本地 tgz 文件**：最简单，但没有固定下载链接、版本记录与公开说明页，不适合「所有 DSH 用户」。
- **公开发布到 npm**：用户按包名安装、可走镜像、能被插件市场 Discover 收录；但需要 registry 发布权限、包名可用性验证与更完整的合规检查，且当前环境无外网，无法先验证。留到 rc 之后。
- **`dsh plugin add github:…` 直装**：需要作者提供自包含的 `prepare` 构建、用户放行构建脚本（等于在用户机器上执行作者代码），体验与信任成本都更高。
- **插件市场索引（Discover）**：索引条目的安装目标只能是 npm 包或 `git+commit`，依赖上面的 npm 方案；且 `plugin-market` bundle 默认未启用。

## 影响

- **安装与升级**：升级 = 再 `add` 一次新版本 tarball + 重启，没有自动更新；设置、Changelist 等 localStorage 数据按页面源保留。
- **发布成本**：每次发布要人工打产物、上传 Release；`make dist` 已把构建、smoke、校验和与安装命令串起来，runbook 规定撤回方式（改 pre-release / 发补丁版本，不重用 tag）。
- **可发现性**：不发布 npm 就无法进入 Discover 市场；需要时另立计划补 npm 与市场索引，不影响 tarball 分发。
- **合规**：Apache-2.0 要求随包分发 `LICENSE`；`NOTICE` 记录版权人。今后若引入第三方代码或图标，必须同步更新 `NOTICE` 与致谢。
- **安全**：Host 代码在 DSH 进程内运行、不受 workspace 沙箱约束，因此只分发可信产物并附 `SHA256SUMS`；Release 说明给出校验命令。
