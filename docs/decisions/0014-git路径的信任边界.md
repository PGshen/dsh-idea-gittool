## 背景

B4d 按负责人的决定，让用户在设置里填 git 的绝对路径：路径存在浏览器里，Git 标签挂载时经 `gitExecutable` 端点交给 Host，Host 校验通过后在进程内存里替换要运行的 git。

整分支终审指出，这等于让任何能调用插件 RPC 的页面代码（包括同一 DSH 页面里的其他客户端插件）选择 Host 运行哪个程序。而 Host 的读命令不经沙箱：一个被采用的假 git 会在每 3 秒一次的轮询里、在沙箱之外运行。最现实的路径是 Agent（可能被提示注入）在会话工作区里写一个打印 `git version …` 的可执行文件，再引导用户把它设成 git 路径。初版校验只看「绝对路径、可执行、`--version` 像 git」，而且为了看 `--version` 先运行了它。

## 决定

保留负责人选的方案（客户端存、Host 内存采用），但把校验收紧成下面的顺序。**前 5 步都通过之前不运行任何东西**：

1. 绝对路径；Windows 上拒绝 UNC/网络路径（`\\…`、`//…`）。
2. 文件名必须是 `git` 或 `git.exe`（不区分大小写），原样和 `realpath` 之后都要满足。
3. `realpath` 之后的文件不能位于会话的沙箱工作区内（`sandboxPolicy.workspaceRoot`），工作区里的文件可能是 Agent 写的。
4. 是普通文件且可执行。
5. 记下 `realpath` 文件的身份（设备号、inode、大小、mtime）。
6. 运行 `<realpath> --version`，必须输出 `git version …` 且不低于最低版本。
7. 之后运行的是 `realpath`，而不是用户填的路径。执行器在每条命令前比对文件身份，文件被替换就不再运行，报 `git/not-found`。

## 考虑过的其他方案

- **只由 Host 环境变量指定（`DSH_GIT_PATH`）、客户端只读显示**：攻击面最小，但用户要改 DSH 的启动方式，「找不到 git」时无法在界面里自助解决。这是负责人待确认 1 的备选 A，未采用。
- **只允许系统目录**（`/usr/bin`、`/opt/homebrew`、`C:\Program Files\Git` 等白名单）：会误伤 asdf/nix/自编译安装，不同平台的列表也难以维护。
- **路径持久化到 Host 的文件**：不能解决「谁能调用端点」的问题，还要新的存储位置。

## 影响

- **仍然存在的风险**：页面上能调用插件 RPC 的代码，可以把 git 指向工作区之外一个已存在、名为 `git` 的可执行文件。这要求攻击者已经能在工作区外写文件，或者那里本来就有这样的文件；这种能力已经超出本插件能防的范围。
- **对用户的影响**：放在工作区里的 git（例如项目自带的工具链）不能用作 git 路径，提示要求选择系统安装的 git。
- 「打印 git 版本的任意程序」不再能通过校验，因为文件名和位置检查在运行之前。

## 补充（2026-10-30，t2 T5）：谁能设置 git 路径；一个写操作只用一个 git

计划：[t2 TODO 设计类修复](../plans/completed/t2-TODO设计类修复.md) T5（AC5–AC7）。负责人已批准。

**背景**：git 路径是 Host 进程级的全局状态（`src/host/index.ts` 只创建一个 `createGitExecutable`），而 `gitExecutable` 端点原先不看会话：只读会话也能换掉所有会话共用的 git。另外执行器每条命令都重新读取当前路径，写队列只按仓库串行，所以一个写操作进行到一半时有人改了路径，这个写操作后面的命令就换成了另一个 git，绕过了写操作开始时做的版本判断（`gitVersionOf`）。

**决定**：

1. **只读会话不能设置 git 路径**（含 `path: null` 清除）。`handleGitExecutable` 先过会话级门禁 `resolveSessionMode`（`src/host/sandbox-gate.ts`）：会话存活 → 沙箱策略可用且能解析 → 模式不是 `read-only`。不通过时返回已有错误码 `git/sandbox-denied`，`details` 带 `mode`、`reasonCode`（如 `read-only-mode`、`session-not-live`、`policy-unavailable`），Host 的 git 不变。
   - 门禁**不看仓库是否在工作区内**：「找不到 git」的会话拿不到仓库，「仓库在沙箱外」的会话写不了仓库，二者都要靠设置 git 路径自救。
   - 门禁之后仍按本 ADR 第 1–7 步校验路径。
2. **按写操作快照**：`GitExecutable.snapshot()` 冻结当时的路径和文件身份；写端点在写队列内、门禁之后取快照，经 `bindWriteContext` 交给这次写的每条命令（`GitRunOptions.executable`），包括写操作内部的读模式查询和 `--version` 探测。之后的 `set()` 只影响下一次写。快照**仍然逐条复核**钉住的文件身份（第 7 步），文件被替换就报 `git/not-found`。读端点不取快照，照旧每条命令读当前路径。
3. **客户端**：挂载时补发已存路径若被拒（`git/sandbox-denied`）不显示错误；设置页在 bootstrap `writePolicy.reasonCode === 'read-only-mode'` 时禁用 git 路径输入并提示「只读会话不能修改 git 路径；请在可写会话中设置」；「未找到 git」空状态在只读会话中隐藏「设置 git 路径」入口（保留安装说明与「重新检测」）。空状态时 bootstrap 失败、拿不到 `writePolicy`，客户端从 Host 拒绝设置（补发或用户点「应用」）的 `reasonCode` 得知只读；此前入口照常显示，拒绝文案由 `gitPathErrorText` 给出。

**考虑过的其他方案**：

- **复用写门禁 `resolveWriteAccess`**：要求仓库在工作区内并做 confine 探针，会把最需要设置路径的两类会话（没有 git、仓库在沙箱外）挡在外面。
- **在 git/not-found 的 bootstrap 错误里附带 writePolicy**：空状态能提前知道只读，但要改 bootstrap 的错误结构；本计划约定协议只新增错误码含义、不改结构，未采用。
- **写操作持有锁、阻止 `set()`**：会让设置路径等待任意长的写（推送可达 180 秒），快照更简单且不阻塞。

**补充（t2 评审 I1）**：只读会话不能靠 `set(null)` 让 Host 重新探测，所以 `info()` 不缓存低于最低版本的探测结果；在 PATH 上原地升级 git 后，「重新检测」（重新 bootstrap）就能看到新版本。

**仍然存在的风险**：`sessionId` 由客户端提供，页面上能调用插件 RPC 的代码可以填一个可写会话的 id 绕过门禁。门禁防的是误用（只读会话里的操作改了全局 git），不是攻击；对攻击的防线仍是本 ADR 第 1–7 步的路径校验。
